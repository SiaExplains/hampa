# Data model

Postgres on Supabase, schema owned by **Drizzle** (`src/db/schema/*.ts`). Migrations generated by `drizzle-kit`, applied via the direct connection. **Nothing is created in the Supabase dashboard.** Every table has RLS enabled with deny-all policies; all access goes through tRPC with the service-role key (see `08-gdpr-and-security.md`).

Conventions: `id uuid default gen_random_uuid()`, `created_at timestamptz default now()`, `updated_at` where rows mutate, snake_case in SQL, camelCase in TS. All timestamps UTC; "week" and "day" logic uses `Europe/Berlin` in code.

## Relationships (summary)

```
cities 1─* users, sports, events
users 1─* events(created_by), invites(inviter), xp_events, gem_events, consents, notifications
sports 1─* sport_coaches, sport_members, events, user_sport_stats
events 1─* event_registrations, attendances, matches
matches 1─* match_players
users *─* users via follows
```

## Erasure rules (per table) — see `08-gdpr-and-security.md`

| Table | On user erasure |
|---|---|
| users | anonymise: username → `deleted_<8hex>`, display_name → "Deleted member", null avatar/bio/telegram, status `deleted`, `deleted_at` set; auth.users row deleted |
| event_registrations, follows, notifications, push_subscriptions, notification_preferences, consents | delete |
| attendances, match_players, xp_events, gem_events, user_sport_stats, user_stats | keep (anonymised via users row) — other members' match history must stay consistent |
| invites (as inviter) | keep, inviter anonymised |
| events (as creator) | keep, creator anonymised |
| audit_log | keep (legal basis: legitimate interest, admin accountability) |
